## Single-purpose statement

This extension has one purpose: to show the signed-in user their own
attendance record from Zoho People, and to remind them when their daily
working-time targets are reached.

It reads the user's attendance for the current and previous month from Zoho
People using the session already signed in to the browser, and presents it in
a popup: today's check-in time, the part-time and full-time checkout targets,
live countdowns to each, hours worked, the quota usage for the current payroll
cycle, and a cycle calendar. It raises a browser notification when a target is
reached, and an early warning when a late check-in means the day will run long.

It does nothing else. It does not write to Zoho, modify any web page, inject
content scripts, or contact any server other than people.zoho.com.

## Permission justifications

One field each on the Privacy tab, 1,000 characters apiece. Written in English:
these go to the review team, not to users.

### storage

Used for chrome.storage.local only, to cache data on the user's own device.

Two things are stored. First, the attendance records fetched from Zoho, so the
popup can paint instantly from cache when opened instead of showing a spinner
while a request is in flight. Second, the user's own settings: interface
language, light/dark mode, colour scheme, their organisation's attendance
policy, and their Zoho portal id.

It also records which reminders have already fired today, so the same
notification is not shown twice.

Nothing is stored remotely. Uninstalling the extension removes all of it.

### alarms

A Manifest V3 service worker is terminated when idle and cannot hold a
setTimeout or setInterval across that termination, so chrome.alarms is the only
way to schedule anything.

Two uses. First, a repeating 15-minute alarm refreshes the cached attendance
data in the background, so the popup is current when the user opens it.
Second, one-shot alarms scheduled for the exact minute a working-time target
falls due, which is what makes the "part-time reached" and "full day complete"
reminders arrive on time rather than whenever the browser happens to wake the
worker.

### cookies

Used to read exactly one cookie: CSRF_TOKEN, scoped to people.zoho.com.

Zoho's attendance endpoint rejects any request that does not echo that cookie
back as a request header. Without reading it, the extension cannot retrieve the
user's own attendance data at all.

The value is used solely as a header on requests to people.zoho.com, and cached
locally so a request can be made while the service worker is starting up. It is
never sent anywhere else, never logged, and never transmitted to the developer
or any third party. No other cookie, and no cookie from any other domain, is
read. It is deleted when the extension is uninstalled.

### notifications

The reminders are the core value of the extension: a user who has to remember
to open a popup to check whether they can leave does not need the extension.

Three notifications, all generated locally from cached data, with no remote
push service involved: one when the part-time target is reached, one when a
full working day is complete, and an early-morning warning when a late check-in
means the full-time target will fall after normal hours.

### host permission — https://people.zoho.com/*

Host permission requested: https://people.zoho.com/*

This is the only host the extension contacts, and the data it exists to
display lives there. It makes GET requests to
https://people.zoho.com/<portalId>/AttendanceViewAction.zp, which returns the
signed-in user's own attendance records for a given month.

The request is authenticated purely by the Zoho session cookie already present
in the user's browser, plus the CSRF_TOKEN header described above. The
extension has no account system, asks for no password, and stores no
credentials.

No content script is injected into this or any other page, and no page is
modified. The permission is used only to fetch the user's own data from the
background service worker.

### remote code

Answer **no**. Everything ships inside the package: no `eval`, no `new
Function`, no remote `script-src`. `test/csp-scan.sh` asserts this against the
built pages on every `pnpm test` run.

## Data usage disclosures (Privacy tab)

- **Collection checkboxes: leave every one unticked.** The store defines
  collection as obtaining data and moving it off the device. Nothing here does
  — attendance records, settings and the CSRF token stay in
  `chrome.storage.local`, and the only host contacted is the one the data came
  from. These disclosures render publicly on the listing, so ticking "Website
  content" would have the store page claim a collection the description denies.
- Judgment call, and the one worth revisiting if a rejection ever names data
  handling: tick **Website content** alone and nothing else. `PRIVACY.md`
  supports either answer. An earlier draft of this file said to tick it as
  _accessed_ — that column does not exist on the form, which is what forced the
  decision.
- Certify all three statements. No sale or transfer to third parties, no use
  beyond the single purpose, no creditworthiness or lending use. All true.
- Privacy policy URL:
  `https://github.com/lelongrvp/zoho-attendance-tracker/blob/develop/PRIVACY.md`
  Note `PRIVACY.md` is not on `main` — main is still the pre-conversion tree —
  so this URL breaks if the default branch ever moves back.

## Review-risk notes (worth knowing before submitting)

- Cookie access + a single-host permission on a third-party site is legitimate
  but gets human review; the justifications above address it directly.
- The endpoint is Zoho's internal `AttendanceViewAction.zp`, not the public
  API. That is not a store violation (it acts on the user's own session), but
  if Zoho changes it the extension breaks until updated — auto-update via the
  store is what makes that survivable for non-tech users.
- Publishing "Unlisted" still requires the full privacy disclosures.
- **Rejected once, 2026-09-15, "Yellow Argon" (keyword spam).** The description
  named all ten colour schemes — Gruvbox, Catppuccin, Nord and the rest — in one
  comma-run. Real features, but a list of well-known theme names reads as search
  keywords to review. It now says "ten built-in colour schemes" and names none.
  No brand-name lists in store metadata, however accurate they are.
- That rejection came from internal human review and cited nothing else — not
  the name, the Zoho trademark, the permissions, or the disclosures. Not proof
  those pass, only that they were not what was flagged.
